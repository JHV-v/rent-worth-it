## 一、做什么（What）

### 1.1 算法结构 —— 从"加权求和"重构为"价值-成本特征推理"

#### 旧结构（v1.6.0 ~ v1.6.2）的问题

```
总分 = 房租×0.30 + 通勤×0.25 + 居住×0.25 + 生活×0.20
     − 压力×0.10
     + cityBonus + contractBonus + happinessBonus    ← 3 个零散加成
```

主要问题：
- 暴力加权求和压缩了维度内信息（7 项居住数据压成 1 个数字）
- 维度间无法交叉，"贵的好房子"和"贵的破房子"在总分上区别不大
- city 同时出现在 房租基准修正 / 压力 / 加成 三处 → 三重计入
- 生活小细节作为表单核心模块之一，却只是零散加成

#### 新结构（v1.6.3）—— 6 维度 + 价值/成本两侧公式

**第一层：6 个维度各自输出特征向量**（不是单纯一个分数，详见 ADR-D11）

```
4 个客观维度：房租、通勤、居住、生活
2 个综合调节指数：压力指数、幸福指数
```

每个维度内部按其子项加权出 mainScore（0-100），有同质子项的维度还输出 weakest / strongest。

**第二层：价值侧 vs 成本侧**

```
价值 = 居住.mainScore × 0.45 + 生活.mainScore × 0.35 + 幸福.mainScore × 0.20

成本 = (100 - 房租.mainScore) × 0.40 + (100 - 通勤.mainScore) × 0.30 + 压力.mainScore × 0.30
       # 房租 / 通勤 分数越低 = 成本越高，所以反转
       # 压力本身是负面指标，不用反转
```

**第三层：总分公式**（价值主导）

```
基础分 = 价值 × 0.65 + (100 - 成本) × 0.35

短板惩罚 = 0
for 每个客观维度 in [房租, 通勤, 居住, 生活]:
    if 维度.mainScore < 30:
        短板惩罚 -= (30 - 维度.mainScore) × 0.3

总分 = clamp(基础分 + 短板惩罚, 0, 100)
```

完整算法 + 17 场景验证：见 [ADR-D10](#adr-d10性价比总分公式--价值主导的非对称加权)。

### 1.2 4 个客观维度详细定义

| # | 维度 | 在价值侧权重 | 在成本侧权重 | 数据源 | 性质 |
|---|---|---|---|---|---|
| 1 | **房租** | — | 0.40 | 房租金额、月薪、城市等级、整租/合租类型 | 财务约束（客观数字） |
| 2 | **通勤** | — | 0.30 | 各出行方式的时长、拖拽优先级 | 时间成本（客观数字） |
| 3 | **居住** | 0.45 | — | 采光、噪音、卫浴、房况、厨房、楼层、水电（7 项） | 房子本身质量（主观感受最丰富） |
| 4 | **生活** | 0.35 | — | 空间感、商超便利、餐饮便利、医疗便利（4 项） | 周边便利度（细分餐饮 / 商超 / 医疗） |

> 注：价值侧 = 用户得到的（居住 + 生活 + 幸福），成本侧 = 用户付出的（房租 + 通勤 + 压力）。

### 1.3 2 个综合调节指数详细定义

| # | 指数 | 在价值侧权重 | 在成本侧权重 | 数据源 | 性质 |
|---|---|---|---|---|---|
| 5 | **压力指数** | — | 0.30 | 高房租、长通勤、低收入、合租、一线城市的"坏处" | 负向综合：日常累在哪里 |
| 6 | **幸福指数** | 0.20 | — | 生活小细节（12 个多选）、合同期稳定性、一线城市的"好处" | 正向综合：日常幸福源 |

**对总分的最大传导**：
- 压力指数 → 总分：100 × 0.30 × 0.35 = **-10.5 分**（成本侧外乘 0.35）
- 幸福指数 → 总分：100 × 0.20 × 0.65 = **+13.0 分**（价值侧外乘 0.65）
- "近似对称"，由"损失厌恶"心理弥补

#### ADR-D1：城市等级"好处归幸福、坏处归压力"

- **背景**：旧算法里城市等级在 3 处影响计算（房租基准修正 / 压力扣分 / cityBonus 加总分），存在三重计入嫌疑，一线城市同时被 +5 总分加成又被 +5 压力扣分，实际净作用接近零。
- **候选方案**：
  - 候选 1：三处合一，只在房租维度修正
  - 候选 2：保留三处但文档化说明
  - **候选 3：拆"好处/坏处"两面 —— 房租基准修正保留（承认事实）、坏处归压力、好处归幸福**
- **选定**：候选 3
- **取舍**：删除独立的 cityBonus 加成，避免三重计入；城市的"双面性"在压力 / 幸福两个调节指数中对称体现，符合用户直觉。

---

#### ADR-D2：压力 / 幸福权重对称（各 0.10 → 价值/成本内部对称）

- **背景**：旧算法只有压力 0.10、没有幸福作为对称项。压力是单边扣分机制。
- **候选方案**：
  - 候选 1：压力 0.10、幸福 0.10（对称）
  - 候选 2：压力 0.15、幸福 0.05（避免痛苦优先）
  - 候选 3：压力 0.05、幸福 0.15（鼓励正面）
- **选定**：候选 1（对称）
- **取舍**：完全对称简洁、便于理解；避免引入价值偏好（"痛苦更重要还是幸福更重要"是哲学问题，算法不预设）。
- **🔧 D9/D10 后的修订**：原"压力 0.10 / 幸福 0.10 直接加总分"在新架构（价值-成本公式）下不成立。**新架构下的对称性表述**：
  - 压力指数 = 成本侧的 30% 内部组成（见 [ADR-D10](#adr-d10性价比总分公式--价值主导的非对称加权) 价值/成本公式）→ 最大传导 -10.5 分
  - 幸福指数 = 价值侧的 20% 内部组成（D10 调整后）→ 最大传导 +13.0 分（详见 [ADR-D7](#adr-d7幸福指数算法细则)）
  - 不再"数字对称"，而是"近似对称"（1.24 倍内），由"损失厌恶"心理弥补

#### ADR-D3：合租额外压力保留

- **背景**：旧算法里合租在两处影响（房租基准 30% → 35% 放宽 + 压力 sharedBurden +6 旧值）。曾质疑双重计入。
- **候选方案**：
  - **候选 1：保留合租压力子项** —— 合租有真实的"室友相处"压力，与房租基准放宽不冲突
  - 候选 2：删除合租压力 —— 合租已在房租维度被补偿
- **选定**：候选 1
- **取舍**：房租基准放宽是"承认你付得起更高比例"（财务承认），合租压力子项是"承认合租有非财务负担"（生活承认），两层语义不重叠。新架构下合租压力的具体数值（`sharedBurden = 60` ∈ 0-100）见 [ADR-D8](#adr-d8压力指数算法细则)。

#### ADR-D4：生活小细节升格为幸福指数核心数据源

- **背景**：旧算法把"生活小细节"（12 个多选标签）作为 totalScore 上的"happinessBonus"零散加成（0/+2/+4 三档），与维度结构脱节。
- **候选方案**：
  - 候选 1：保留为加成
  - **候选 2：升格为幸福指数的核心数据源**
- **选定**：候选 2
- **取舍**：生活小细节本来就是表单核心模块之一，结构上理应有"维度归属"；升格后允许更细致的算法设计，具体算法见 [ADR-D7](#adr-d7幸福指数算法细则)。

#### ADR-D5：生活维度扩源（A+D 组合 + 重命名）

- **背景**：生活维度当前只有 2 个数据源（空间感、周边便利度），但在旧加权求和结构下权重占 0.18（D9 重构后改为价值侧 0.35）。单项标签影响过大（选错"空间感"可能拖动总分 5+）。"周边便利度"语义模糊（既含商超也含餐饮），无法精细评价。
- **候选方案**：
  - 候选 1：不扩源，接受"生活维度只有 2 项"（降低权重）
  - 候选 2（保守）：加安全感 1 项
  - **候选 3（中等）：加餐饮便利 + 医疗便利 2 项，并把"周边便利度"重命名为"商超便利"**
  - 候选 4（激进）：加安全感 + 餐饮 + 公园 3 项
- **选定**：候选 3（中等扩源）
- **取舍**：
  - 表单加 2 个新选项块（+10-15 秒填表时间），用户负担可接受
  - "周边便利度"语义模糊问题一并解决（重命名为"商超便利"）
  - 医疗低频但重要，覆盖"有家人 / 慢性病" 用户群
  - 4 项数据源的权重分布让单项最大影响（在 D9/D10 新架构下）降到 ~7 分（原 2 项时单项最大 ~10+ 分）

**具体设计**：

| 字段 key | 中文名 | 权重 | 表单选项 | 映射 (1-5) |
|---|---|---|---|---|
| `space` | 空间感 | 0.30 | 拥挤 / 偏小 / 刚好 / 宽敞（保持现状，4 档均无"中性"选项，跳过 3） | 1/2/4/5 |
| `convenience` | 商超便利 *（旧 `food` 字段重命名）* | 0.25 | 很方便 / 一般 / 不方便（保持现状） | 5/3/1 |
| `dining` | 餐饮便利 *（新增）* | 0.25 | 多 / 适中 / 少 | 5/3/1 |
| `medical` | 医疗便利 *（新增）* | 0.20 | 近（步行 15 分钟内）/ 一般（公共交通可达）/ 远（需打车以上） | 5/3/1 |
| **合计** | | **1.00** | | |

**数据变更影响**（将在第 3 节"怎么做"详述）：
- `RawScoreInput` 类型增加 `dining` / `medical` 字段，删除 `food` 改为 `convenience`（破坏性变更）
- `LIFE_WEIGHTS` 改为 4 项
- 表单 RentForm 加 2 个 TagSelectGroup
- adapter 透传 2 个新字段
- `STORAGE_VERSION` 升级（避免旧 sessionStorage 错位）

#### ADR-D6：合同期归入幸福指数

- **背景**：旧算法把合同期作为独立的 contractBonus（半年 -3 / 1年 0 / 2年+ +3），幅度小（±3），且作为"零散加成"与新结构不一致。
- **候选方案**：
  - **候选 1：归入幸福指数（合同期 = 稳定感 → 幸福子项）**
  - 候选 2：保持独立加成（不变）
  - 候选 3：删除（合同期不影响评分）
  - 候选 4：归入压力指数（短期合同 = 不稳定压力源）
- **选定**：候选 1（归入幸福指数）
- **取舍**：
  - 与 D4 一致：所有"加分类"信号统一归到幸福指数，结构干净
  - 短期合同的"压力"语义弱（一般不是租客主动选择），不适合归压力
  - 删除会让用户觉得"我选了合同期但没用"，不符合体感

**子项设计**（详见 ADR-D7 幸福指数算法）：
- 半年 → 0 分（"被迫"短租，无幸福加成）
- 1年 → 50 分（基准）
- 2年+ → 100 分

#### ADR-D7：幸福指数算法细则

- **背景**：D4/D5/D6 把多个零散加分项汇总到幸福指数，需要明确内部权重与子项映射函数。
- **候选方案**（**幸福指数内部** 3 子项权重）：
  - 候选 1（生活小细节主导）：0.60 / 0.20 / 0.20
  - **候选 2（三足鼎立）：0.40 / 0.30 / 0.30**
  - 候选 3（去合同期化）：0.70 / 0.10 / 0.20
- **选定**：候选 2（三足鼎立）
- **取舍**：三个数据源功能不同，三足鼎立避免任一项独大；生活小细节虽然是用户主动勾选，但 12 项标签的累加效应已经很强，不需要再放大权重。

> 📌 **内外权重区分**：上述 0.40/0.30/0.30 是幸福指数 **内部** 三子项权重（合计 1.00）。幸福指数本身在价值侧的**外部**权重为 0.20（由 ADR-D10 决定）。两者复合后，幸福对总分的最大传导 = 100 × 0.20 × 0.65 = +13 分。

**子项算法**（v1.6.3 修订：解决"幸福永远 ≥ 15"的语义错位）：

| 子项 | 内部权重 | 数据源 | 0-100 分映射规则 |
|---|---|---|---|
| **生活小细节** (`lifeDetails`) | 0.40 | 12 个多选标签的勾选数量（`input.lifeDetails`，整数 0-12） | `count × 100/12`（线性：0 项 → 0 / 6 项 → 50 / 12 项 → 100） |
| **合同期** (`contractBenefit`) | 0.30 | `input.contractTerm`（1/2/3） | `CONTRACT_BENEFIT[contractTerm]`：**半年 → 0 / 1年 → 50 / 2年+ → 100**（中性线性，半年 = 无加成） |
| **城市好处** (`cityBenefit`) | 0.30 | `input.cityType`（1-5） | `CITY_BENEFIT[cityType]`：**一线 → 100 / 新一线 → 67 / 二线 → 33 / 三线及以下 → 0**（线性，三线 = 无加成） |

**幸福指数 = lifeDetails_score × 0.40 + contractBenefit_score × 0.30 + cityBenefit_score × 0.30**

**最低组合**（0 项 + 半年 + 三线及以下）：
- lifeDetails: 0 × 0.40 = 0
- contractBenefit: 0 × 0.30 = 0
- cityBenefit: 0 × 0.30 = 0
- **幸福指数 = 0** ✅（解决了"幸福永远 ≥ 15"的语义错位）

**示例**：用户勾选 6 项生活小细节 + 1年合同 + 二线城市
- lifeDetails: 50 × 0.40 = 20
- contractBenefit: 50 × 0.30 = 15
- cityBenefit: 33 × 0.30 = 9.9
- **幸福指数 = 44.9**
- 对总分的传导：44.9 × 0.20 × 0.65 = **+5.84 分**（D9/D10 新架构下）

**最大幸福贡献**：勾满 12 项 + 2年+ + 一线 → 100 × 0.20 × 0.65 = **+13.0 分**（新架构）

- **🔧 D9/D10 后的修订**：原"幸福指数 × 0.10 加总分"在新架构下不成立。新架构下：
  - 幸福指数 = 价值侧 20% 内部组成（由 ADR-D10 修订为 0.45/0.35/0.20）
  - 最大幸福对总分的传导：100 × 0.20 × 0.65 = **+13.0 分**
  - 内部 3 子项权重（lifeDetails 0.40 / contractBenefit 0.30 / cityBenefit 0.30）**保持不变**——子项之间的相对关系不变，只是整个幸福指数对总分的"放大系数"调了

#### ADR-D8：压力指数算法细则

- **背景**：旧算法的压力指数把 5 个子项的"扣分值"直接累加成 rawScore（可能 > 100），与"0-100 维度分"的整体设计不一致。需要与幸福指数对称设计（每子项先映射 0-100，再加权）。
- **候选方案**（**压力指数内部** 5 子项权重）：
  - 候选 A：均分 5×0.20
  - **候选 B：房租通勤主导** 0.30 / 0.30 / 0.15 / 0.10 / 0.15
  - 候选 C：经济主导 0.35 / 0.15 / 0.30 / 0.10 / 0.10
- **选定**：候选 B
- **取舍**：高房租 / 长通勤是用户每天最直观感受到的压力，权重应该高；低收入是隐性压力（不天天感受）；合租和城市坏处幅度较小但保留区分度。

> 📌 **内外权重区分**：上述 0.30/0.30/... 是压力指数 **内部** 五子项权重（合计 1.00）。压力指数本身在成本侧的**外部**权重为 0.30（由 ADR-D10 决定）。两者复合后，压力对总分的最大传导 = 100 × 0.30 × 0.35 = -10.5 分。

**子项算法**：

| 子项 | 内部权重 | 数据源 | 0-100 分映射规则 |
|---|---|---|---|
| **高房租** (`rentBurden`) | 0.30 | rentRatio = `input.rent / max(input.income, 1) × 100`（房租占月薪百分比；与 D12c 一致，max 防御 income=0 异常） | `(ratio - 20) × 3`，clamp [0, 100] |
| **长通勤** (`commuteBurden`) | 0.30 | `input.commuteWeighted`（**疲惫度分钟数**，由 adapter 按 D12d Step 1 的系数与位置权重加权，已非纯总时长） | `(fatigue - 30) × 1`，clamp [0, 100]。注：阈值 30 是"疲惫度 30"，约等于步行 30 分钟或公共交通 28.6 分钟 |
| **低收入** (`incomeBurden`) | 0.15 | `input.income`（月薪，元） | `(15000 - income) / 150`，clamp [0, 100] |
| **合租** (`sharedBurden`) | 0.10 | `input.housingType` | 整租 → 0 / 合租 → 60 / unknown → 0（不区分主次卧；unknown 按整租宽松处理） |
| **城市坏处** (`cityBurden`) | 0.15 | `input.cityType`（1-5） | `CITY_BURDEN[cityType]`：一线 → 80 / 新一线 → 50 / 二线 → 20 / 三线及以下 → 0 |

**压力指数 = rentBurden × 0.30 + commuteBurden × 0.30 + incomeBurden × 0.15 + sharedBurden × 0.10 + cityBurden × 0.15**

**示例 1**：月薪 8000、房租 3500、通勤疲惫度 60min、整租、二线城市
- rentBurden: (43.75 - 20) × 3 = 71.25
- commuteBurden: (60 - 30) × 1 = 30
- incomeBurden: (15000 - 8000) / 150 = 46.7
- sharedBurden: 0
- cityBurden: 20
- 压力指数 = 71.25×0.30 + 30×0.30 + 46.7×0.15 + 0×0.10 + 20×0.15 = 21.4 + 9 + 7 + 0 + 3 = **40.4**
- 对总分的传导：-40.4 × 0.30 × 0.35 = **-4.24 分**（D9/D10 新架构下）

**示例 2（极端）**：月薪 5000、房租 4500（占 90%）、通勤 130min、合租、一线城市
- rentBurden: (90 - 20) × 3 = 100（封顶）
- commuteBurden: (130 - 30) × 1 = 100（封顶）
- incomeBurden: (15000 - 5000) / 150 = 66.7
- sharedBurden: 60
- cityBurden: 80
- 压力指数 = 100×0.30 + 100×0.30 + 66.7×0.15 + 60×0.10 + 80×0.15 = 30 + 30 + 10 + 6 + 12 = **88**
- 对总分的传导：-88 × 0.30 × 0.35 = **-9.24 分**

**最大压力贡献**：5 项都封顶 100 → 100 × 0.30 × 0.35 = **-10.5 分**（新架构下）。
合租封顶 60 让现实可达上限略低，但与极端房租 + 长通勤 + 一线 + 极低收入叠加时已经接近 -10.5 分天花板。

- **🔧 D9/D10 后的修订**：原"压力指数 × 0.10 扣总分"在新架构下不成立。新架构下：
  - 压力指数 = 成本侧 30% 内部组成（ADR-D10 公式不变）
  - 最大压力对总分的传导：100 × 0.30 × 0.35 = **-10.5 分**
  - 内部 5 子项权重（房租 0.30 / 通勤 0.30 / 收入 0.15 / 合租 0.10 / 城市 0.15）**保持不变**

#### ADR-D9：算法架构升级 —— 从"加权求和"升级为"特征推理"

> ⚠️ 这是 v1.6.3 最根本的架构决策。在它之上，D2/D7/D8 已加入 🔧 修订段对齐新架构。

- **背景**：D1-D8 的设计都基于"每个维度独立打分 0-100 → 加权求和 → 总分"的传统结构。但讨论中发现这种结构有 3 个根本问题：
  - **信息丢失严重**：把 7 项居住数据压成 1 个数字，损失了"哪项最差 / 哪项最好"等细节
  - **维度间无法交叉**：旧结构下"贵的好房子"和"贵的破房子"在总分上区别不大
  - **算法目标"性价比"无法用简单加权表达**：性价比天然是"价值 vs 成本"的关系，而非线性加权
- **候选方案**：
  - 候选 1（旧）：维度独立打分 → 加权求和
  - 候选 2：维度独立打分 + 总分用"价值 - 成本"或"价值 / 成本"等交叉公式
  - **候选 3：维度内子项分保留 + 特征向量表示 + 总分用特征推理（推荐）**
- **选定**：候选 3
- **取舍**：
  - **专业性大幅提升**：算法不再是"暴力打分"，能反映复杂的"哪好哪不好"
  - **诊断可解释性增强**：Modal 能讲"你的总分被居住维度的最弱项楼层拖累"
  - **代价**：实施复杂度提升、需要更多测试覆盖、调参更难
  - 用户在 v1.6.1-v1.6.2 反复发现"分数不动"或"分数不合理"的根因就是旧结构信息丢失太多，必须根本性升级才能解决

**架构三层结构**：

```
[第 0 层] 用户原始输入
            │
            ▼  归一化（不丢信息）
[第 1 层] 子项分数集合（有同质子项的维度才有；无同质子项的维度走整体公式）
   - 房租维度：整体公式（D12c），输入 rentRatio / cityModifier / housingType，无子项分数
   - 通勤维度：整体公式（D12d），输入 fatigueWeighted / totalMinutes，无子项分数
   - 居住维度：7 项各自 0-100（采光/噪音/卫浴/房况/厨房/楼层/水电）
   - 生活维度：4 项各自 0-100（空间感/商超便利/餐饮便利/医疗便利）
   - 压力指数：5 项各自 0-100（房租压力/通勤压力/收入压力/合租压力/城市压力）
   - 幸福指数：3 项各自 0-100（生活小细节/合同期/城市好处）
            │
            ▼  维度内聚合
[第 2 层] 维度特征向量
   每个维度输出一组数据，可能包括（具体由 D11 决定）：
   - mainScore：主分（传统的加权平均）
   - weakest：最弱子项 { key, label, score }
   - strongest：最强子项 { key, label, score }
   - dispersion：分数离散度（标准差）  ← D11 候选 C 暂不实现
   - completeness：数据完整度（填写率）  ← D11 候选 C 暂不实现
            │
            ▼  跨维度推理
[第 3 层] 性价比总分 + 诊断输出
   用 6 个维度的特征向量综合推理
   公式形式："价值 vs 成本" 的非对称加权（具体见 [ADR-D10](#adr-d10性价比总分公式--价值主导的非对称加权)）
```

**后续 ADR 完成情况**：
- 第 2 层每个维度的"特征向量"具体字段 → 已在 [ADR-D11](#adr-d11维度特征向量定义) 确定（mainScore + weakest + strongest）
- 第 3 层"价值 vs 成本"的总分公式 → 已在 [ADR-D10](#adr-d10性价比总分公式--价值主导的非对称加权) 确定（价值×0.65 + (100-成本)×0.35 + 短板惩罚）
- D1-D8 在新架构下的修订 → 已在 [D2](#adr-d2压力--幸福权重对称各-010--价值成本内部对称) / [D7](#adr-d7幸福指数算法细则) / [D8](#adr-d8压力指数算法细则) 加入 🔧 修订段
- 4 个客观维度的内部算法 → 已在 [D12a-D12d](#adr-d12a居住维度内部算法) 确定

#### ADR-D10：性价比总分公式 —— 价值主导的非对称加权

- **背景**：在 D9 架构下，6 个维度的特征产出后，需要总分公式把它们综合成 0-100 的性价比分。最初尝试"价值减成本"（X 公式），但测试发现"贵的好房子"与"便宜的破房子"分差仅 5 分，太接近、不符合"两种完全不同体验"的直觉。后又尝试 0.7/0.3 价值主导，发现 80 区间偏少。最终选定 0.65/0.35，让 80 档容纳更多用户。
- **候选方案**：
  - 候选 X：基础分 = 50 + (价值 - 成本) / 2（→ 两类房子差距太小）
  - 候选 Y：基础分 = 价值 / 成本 × 50（ROI 性质，需处理除零）
  - 候选 Z：维度乘法 (短板效应)（→ 任一维度低 = 总分严重压低，过于苛刻）
  - 候选 W (0.7/0.3)：价值×0.7 + (100-成本)×0.3（→ 80 区间偏少）
  - **候选 W' (0.65/0.35)：价值×0.65 + (100-成本)×0.35（推荐）**
- **选定**：候选 W'（价值主导 0.65/0.35）
- **取舍**：
  - 体现"算法更看重你得到了什么，而非你付了什么"的产品哲学
  - 贵的好房子（70）与便宜的破房子（53）拉开 ~17 分差距，符合直觉
  - 80 档位被打开（80-89 档约占 12%；含 90+ 优秀档合计约 29%）
  - 保留 4 客观维度短板惩罚（任一维度 < 30 → 按差距扣分）

**完整算法**：

```
[第 1 步] 价值侧（用户得到的）
价值 = 居住.mainScore × 0.45
     + 生活.mainScore × 0.35
     + 幸福.mainScore × 0.20
     # 注：D10 初稿曾用 0.40/0.30/0.30；后调整为 0.45/0.35/0.20
     # 目的：让幸福对总分的最大传导从 19.5 降到 13，与压力 10.5 接近对称

[第 2 步] 成本侧（用户付出的，反转：分数越低=成本越高，所以 100-X）
成本 = (100 - 房租.mainScore) × 0.40
     + (100 - 通勤.mainScore) × 0.30
     + 压力.mainScore × 0.30
     # 压力本身就是负面指标，不用反转

[第 3 步] 基础分（价值主导）
基础分 = 价值 × 0.65 + (100 - 成本) × 0.35

[第 4 步] 短板惩罚
短板惩罚 = 0
for 每个客观维度 in [房租, 通勤, 居住, 生活]:
    if 维度.mainScore < 30:
        短板惩罚 -= (30 - 维度.mainScore) × 0.3
    # 维度.mainScore = 0 → 扣 9 分
    # 维度.mainScore = 20 → 扣 3 分
    # 维度.mainScore = 30 → 扣 0 分

[第 5 步] 总分
总分 = clamp(基础分 + 短板惩罚, 0, 100)
```

**对总分的传导上限**（重要修订）：
- 幸福最大传导：100 × 0.20 × 0.65 = **+13.0 分**
- 压力最大传导：100 × 0.30 × 0.35 = **-10.5 分**
- 比值约 1.24，**近似对称**（不严格相等，因为价值主导 0.65 > 成本占比 0.35）
- 这种"轻微不对称"被"损失厌恶"心理学规律弥补（扣 1 分痛感大于加 1 分快感）

**标准测试场景集**（17 个场景，覆盖 5k-50k 月薪、4 档城市等级、整租/合租）：

#### ADR-D11：维度特征向量定义

- **背景**：ADR-D9 提出"每个维度输出特征向量"概念，但具体字段未定。D10 总分公式实际只用了 mainScore；诊断 Modal 还需要 weakest / strongest 用于"强项 / 短板"文案。
- **候选方案**：
  - 候选 A：最小集（mainScore + weakest + strongest）
  - 候选 B：完整集（+dispersion + completeness）
  - 候选 C：渐进集（先 A，未来需要时再加）
- **选定**：候选 C（即当前 = 候选 A）
- **取舍**：
  - 总分公式 (D10) 不依赖 dispersion / completeness，过早引入是过度设计
  - 诊断 Modal 需要 weakest / strongest，必要
  - 渐进允许未来需要时无痛扩展

**特征向量类型定义**：

```typescript
type DimensionSubItem = {
  key: string       // 子项代号，如 'sunlight'
  label: string     // 用户可见名，如 '采光'
  score: number     // 0-100
}

type DimensionFeature = {
  mainScore: number                       // 0-100，维度的总评
  weakest?: DimensionSubItem | null       // 最弱子项（仅有同质子项的维度）
  strongest?: DimensionSubItem | null     // 最强子项（仅有同质子项的维度）
}
```

**各维度的字段配置**：

| 维度 | mainScore | weakest | strongest | 子项数 |
|---|---|---|---|---|
| **房租** | ✅ | ❌ | ❌ | 无同质子项 |
| **通勤** | ✅ | ❌ | ❌ | 无同质子项（疲惫度 + bonus 不同质） |
| **居住** | ✅ | ✅ | ✅ | 7 项（采光、噪音、卫浴、房况、厨房、楼层、水电） |
| **生活** | ✅ | ✅ | ✅ | 4 项（空间感、商超便利、餐饮便利、医疗便利） |
| **压力指数** | ✅ | ✅ | ✅ | 5 项（房租压力、通勤压力、收入压力、合租压力、城市压力） |
| **幸福指数** | ✅ | ✅ | ✅ | 3 项（生活小细节、合同期、城市好处） |

**诊断 Modal 文案模板**：

| 维度 | 性质 | 文案模板 |
|---|---|---|
| 居住 | 正向 | `'居住强项：{strongest.label}'` / `'居住短板：{weakest.label}'` |
| 生活 | 正向 | `'生活强项：{strongest.label}'` / `'生活短板：{weakest.label}'` |
| 幸福指数 | 正向 | `'最大幸福源：{strongest.label}'` / `'最少幸福源：{weakest.label}'` |
| 压力指数 | **负向** | `'最大压力源：{strongest.label}'` / `'最小压力源：{weakest.label}'` |
| 房租 / 通勤 | — | 不展示 strongest/weakest，只给 mainScore + 文字总结 |

**weakest/strongest 的计算规则**：

```
对于每个有同质子项的维度：
1. 计算所有子项的 (子项分 × 子项内部权重) → 贡献值（contribution）
2. weakest = 贡献值最低的子项                     【选取看"对维度总分的相对影响"】
3. strongest = 贡献值最高的子项
4. 若两个子项贡献值相等，按 key 字母顺序取靠前的
5. 阈值过滤（应用于"语义上的强项/短板"，看子项的"绝对水平 score"）
```

> 📌 **为什么混用两个标准**：
> - 选取用"贡献值"：避免"采光 60 分但权重 0.20" 被"水电 50 分但权重 0.08"错挤掉——前者对维度总分影响远大；
> - 过滤用"score"：决定的是"该不该展示这个标签"——score 80+ 实际就是"好"，无论权重多低；score 30- 实际就是"差"。这是绝对语义判断，不该被权重稀释。

**⚠️ 正向 / 负向维度的语义差异**（重要）：

- **正向维度**（居住 / 生活 / 幸福）：子项分越高越好 → `strongest` 是"用户最得意的方面"、`weakest` 是"短板"
- **负向维度**（压力指数）：子项分越高 = 压力越大 → `strongest` 是"**最大的压力来源**"、`weakest` 是"最小的压力来源"

阈值过滤规则（注意：数字规则**正负向通用**，因为 score 自身的语义已经反映了"分高=好/分高=压大"的差异）：

| 维度性质 | strongest = null 条件 | weakest = null 条件 | 不展示的语义 |
|---|---|---|---|
| 正向（居住/生活/幸福） | 所有子项 score ≤ 30 | 所有子项 score ≥ 80 | 全员差就没"强项"；全员好就没"短板" |
| 负向（压力指数） | 所有子项 score ≤ 30 | 所有子项 score ≥ 80 | 全员低压力就没"最大压力源"；全员高压力（极端罕见）就没"最小压力源"展示价值 |

**注意**：
- weakest/strongest 用的是"贡献值"（分数 × 权重），不是单纯分数。因为权重低的子项即使分数低/高，对维度总分影响也有限。
- 阈值过滤避免违和文案：完美用户的居住维度不会被强行说"短板是水电"；整租用户的压力维度（sharedBurden=0）不会被说"最大压力是合租"。

#### ADR-D12a：居住维度内部算法

> 📌 **注意"内外权重"区分**：下文权重是居住**维度内部**的子项权重（合计 1.00），与 D10 中居住维度在**价值侧**的外部权重 0.45 不同。两者复合：居住对总分的最大传导 = 100 × 0.45 × 0.65 = +29.25 分。

- **背景**：居住维度有 7 个同质子项（采光、噪音、卫浴、房况、厨房、楼层、水电）。v1.6.0 起的旧权重 0.22/0.20/0.16/0.15/0.12/0.10/0.05，最高最低差 4.4 倍。需要决定是否调整。
- **候选方案**：
  - 候选 A：维持现状 0.22/0.20/0.16/0.15/0.12/0.10/0.05（4.4 倍差距）
  - 候选 B：扁平化 0.18/0.17/0.15/0.14/0.13/0.12/0.11（1.6 倍差距，几乎均匀）
  - **候选 C：温和折中 0.20/0.18/0.16/0.15/0.13/0.10/0.08（2.5 倍差距，保留区分度）**
- **选定**：候选 C
- **取舍**：
  - 候选 B 过度扁平，让"水电 0.11" 和"采光 0.18" 几乎对等，不符合"采光是高频体感、水电只是月费差"的直觉
  - 候选 C 缩小最高/最低权重差，但保留"采光、噪音是核心，水电是边缘"的层级
  - "无窗用户" 在候选 C 下扣分依然明显（不会因权重稀释而失真）

**子项算法**：

| 子项 (key) | 权重 | 数据源 | 映射规则 |
|---|---|---|---|
| `sunlight` 采光 | 0.20 | 1-5 标签字典 | scaleFromFive：1→0/2→25/3→50/4→75/5→100 |
| `noise` 噪音（反向） | 0.18 | 1-5 标签字典 | reverseFromFive：1→100/2→75/3→50/4→25/5→0 |
| `bathroom` 卫浴 | 0.16 | 标签字典 | scaleFromFive |
| `condition` 房况 | 0.15 | 标签字典 | scaleFromFive |
| `kitchen` 厨房 | 0.13 | 标签字典 | scaleFromFive |
| `floor` 楼层 | 0.10 | 4 档标签 | scaleFromFive |
| `utility` 水电 | 0.08 | 2 档标签 | scaleFromFive |
| **合计** | **1.00** | | |

**居住.mainScore = Σ(子项分 × 子项权重)**，clamp [0, 100]

**特征向量输出**（按 [ADR-D11](#adr-d11维度特征向量定义)）：

- `weakest`：贡献值（子项分 × 权重）最低的子项；若所有子项 ≥ 80 则为 null
- `strongest`：贡献值最高的子项；若所有子项 ≤ 30 则为 null

#### ADR-D12c：房租维度内部算法

> 📌 **注意"内外权重"区分**：本算法输出的是房租维度的 mainScore（0-100）。房租维度在成本侧的外部权重为 0.40，对总分的最大传导 = 100 × 0.40 × 0.35 = -14 分（房租 0 分时）。

- **背景**：v1.6.1-v1.6.2 房租维度使用 13 档分段插值（RENT_SEGMENTS），存在"塌顶 / 塌底 / 跨段跳变"等问题。讨论过 K/M/I+/N/O/P 等多种候选；D9 重构后房租维度职责简化为"反映房租在购买力/城市下的合理性"，不再承担性价比。
- **候选方案**：
  - 候选 A：保留 13 档分段插值（现状）
  - 候选 M：基础函数 + 多项修正（专业但复杂，调参难）
  - 候选 sigmoid：S 曲线全程敏感（基准点 = 80，跨基准骤降，争议大）
  - 候选 I+：双侧高斯衰减（低占比也扣分，与"算法不评价便宜原因"矛盾）
  - **候选 K：低占比饱和 100 + 高占比 exp 衰减**
- **选定**：候选 K
- **取舍**：
  - K 数学简洁（一行公式）、语义清晰（基准内不评价 / 基准外按客观财务压力扣分）
  - K 算法中立，不替用户判断"为什么便宜"（朋友的房 / 公司补贴 / 远郊都不评价）
  - **死区代价**：低占比段（offset ≤ 0）月薪变化无法体现在房租维度，但通过压力指数 incomeBurden 间接体现
  - 传导测试：跨基准场景 K 在总分上能动 3-4 分，敏感度足够

**算法**：

```
[Step 1] rentRatio = input.rent / max(input.income, 1) × 100
         # 防御：income ≤ 0 在 normalize 层已 clamp 到 1，
         #       这里 max() 是双保险，避免 Infinity / NaN 污染下游
[Step 2] baseline = (input.housingType === 'shared' ? RENT_BASELINE_SHARED : RENT_BASELINE_WHOLE)
                  + getCityModifier(input.cityType).rent
         # 注：input.housingType === 'unknown' 视为 'whole'（不放宽基准）
         # cityModifier.rent: 一线 +8 / 新一线 +4 / 二线 0 / 三线及以下 -4
         # 用 getCityModifier 兜底，避免 input.cityType 异常值（0/6+）崩溃
[Step 3] offset = rentRatio - baseline
[Step 4] mainScore:
         if offset ≤ 0:  score = 100
         if offset > 0:  score = 100 × exp(-offset / RENT_DECAY)   # RENT_DECAY = 15
```

**效果对照表**：

| offset | 含义 | mainScore |
|---|---|---|
| ≤ 0 | 低于或贴近基准 | **100** |
| +3 | 略高 | 81.9 |
| +5 | 略偏紧 | 71.7 |
| +10 | 偏紧 | 51.3 |
| +15 | 紧 | 36.8 |
| +20 | 压力大 | 26.4 |
| +30 | 极紧 | 13.5 |
| +50 | 崩盘 | 3.6 |
| +100 | 极端 | 0.1 |

**特征向量输出**（按 [ADR-D11](#adr-d11维度特征向量定义)）：
- `mainScore`：上述公式
- `weakest` / `strongest`：**不输出**（房租维度没有同质子项）

#### ADR-D12d：通勤维度内部算法

> 📌 **注意"内外权重"区分**：本算法输出的是通勤维度的 mainScore（0-100）。通勤维度在成本侧的外部权重为 0.30，对总分的最大传导 = 100 × 0.30 × 0.35 = -10.5 分（通勤 0 分时）。

- **背景**：v1.6.x 通勤维度使用 `baseScore = 100 × exp(-fatigue/60) + bonus(短+5 / 长-10 / 极端-25)`。问题：(1) exp 衰减太快，30min 通勤只能拿 66 分，与"短通勤体感舒适"直觉不符；(2) bonus 不对称（+5 vs -25），与 D2 对称哲学不一致；(3) 120+min 后 clamp 到 0，失去极端通勤的区分度。
- **候选方案**：
  - 候选 0：保持现状
  - **候选 1：调慢 exp（系数 60→100）+ 对称 bonus（+10/0/-10/-20）**
  - 候选 2：完全用分段插值替代 exp
  - 候选 3：仅调 exp 系数 60→80
  - 候选 4：双阶段函数
- **选定**：候选 1
- **取舍**：
  - 调慢 exp 让短通勤获得合理高分（30min → 84 分）
  - 对称 bonus 与 [D2 修订后的"近似对称"哲学](#adr-d2压力--幸福权重对称各-010--价值成本内部对称)一致
  - 数学结构与现状接近，迁移成本低（只调系数）
  - 仍保留极端段 clamp（180min+ 接近 0），不让极端用户感觉算法失灵

**算法**：

```
[Step 1] fatigueWeightedMinutes = input.commuteWeighted
         # ⚠️ 不在 commute.ts 内重新加权！adapter.ts 已按下述公式算好：
         #   adapter: fatigueWeighted = Σ(模式时长 × 模式系数 × 位置权重)
         #   模式系数：步行 1.0 / 骑行 0.95 / 公共交通 1.05 / 驾车 1.10
         #             （定义在 COMMUTE_FATIGUE_COEFFICIENT）
         #   位置权重：[1.0, 0.7, 0.4, 0.2]（拖拽顺序由用户决定，定义在 COMMUTE_POSITION_WEIGHTS）
         # commute.ts 仅消费这个加权结果，避免双重加权。

[Step 2] totalMinutes = input.commuteTotalMinutes
         # 同样由 adapter 算好（Σ 模式时长，不加权）

[Step 3] baseScore = 100 × exp(-fatigueWeightedMinutes / 100)
         # 衰减系数从 60 → 100（更平缓）

[Step 4] bonus（基于 totalMinutes）：
         ≤ 30 min  → +10  （短通勤奖励）
         ≤ 60 min  → 0    （中性）
         ≤ 90 min  → -10  （长通勤惩罚）
         > 90 min  → -20  （极端惩罚）

[Step 5] mainScore = clamp(baseScore + bonus, 0, 100)
```

**效果对照表**（以"全步行"为例，疲惫度 = 总时长 × 1.0）：

| 总时长 | 疲惫度 | baseScore | bonus | mainScore |
|---|---|---|---|---|
| 15 min | 15 | 86 | +10 | **96** |
| 30 min | 30 | 74 | +10 | **84** |
| 45 min | 45 | 64 | 0 | **64** |
| 60 min | 60 | 55 | 0 | **55** |
| 90 min | 90 | 41 | -10 | **31** |
| 120 min | 120 | 30 | -20 | **10** |
| 180 min | 180 | 17 | -20 | **0**（clamp） |

**特征向量输出**（按 [ADR-D11](#adr-d11维度特征向量定义)）：
- `mainScore`：上述公式
- `weakest` / `strongest`：**不输出**（通勤维度的"疲惫度 + bonus"不同质）

### 1.5 公式终极版

```
[第 1 步] 计算 6 个维度的特征向量（每个含 mainScore，部分含 weakest/strongest）
```

## 二、为什么（Why）

> 本节回答"为什么这么改"。每个 ADR 内部的"取舍"段已经讲了局部理由，本节聚焦**全局视角**：重构的必要性、架构选型的逻辑、权重设计的产品哲学，以及"哪些诱人想法被放弃"。

### 2.1 为什么要在 v1.6.3 推倒重构

**症状层**：v1.6.0 上线后到 v1.6.2，用户在使用中反复发现两类令人不适的现象：
- **"分数不动 / 区分度不足"**：表单选项的小幅改动（采光、月薪、楼层等单项变化）在总分上几乎看不到差异，13 档分段插值更存在"塌段"——同一档内任意挪动数值都不影响分数。
- **"分数不合理"**：高房租 + 顶级好房（如"一线 1.5w 贵的好房子"）和便宜破房（"二线 1.2w 便宜破房"）在旧算法下分差被压缩到个位数，与用户的真实体感"两种完全不同的居住方式"严重背离。

**根因层**：表层 bug 只是冰山一角。回看 [v1.6-algorithm-audit.md](./v1.6-algorithm-audit.md) 列出的 17 个问题点，**80% 都指向同一个深层缺陷——"暴力加权求和"心智模型不适合"性价比"评价**：

| 根因 | 表层症状（举例） |
|---|---|
| 信息丢失：把 7 项居住数据压成 1 个 `liveScore` | 居住单项变化稀释；"哪项最差"无法诊断 |
| 维度不交叉：4 维独立打分再加权 | 贵的好房子 vs 便宜的破房子分差不大 |
| 三重计入：city 同时出现在 房租基准 / 压力 / cityBonus | 一线城市的"贵 + 累 + 机会多"被同时算 3 次但互相抵消 |
| 零散加成：cityBonus / contractBonus / happinessBonus 直接加总分 | 用户改"生活小细节"标签，总分最多动 +4（0/+2/+4 三档） |

**结论层**：v1.6.0 → v1.6.2 已经针对 17 个问题点做了**局部小修**（调权重、调分段、加 bonus 上限），但每次修都按下葫芦浮起瓢——根本问题不在某个具体公式，**在心智模型不对**。

继续小修需要至少 17 个 patch、还会引入新的耦合；而换心智模型（从"打分"换成"特征推理"，详见 D9）只需做一次根本性改动。**v1.6.3 选择后者**：宁可付出 6 个算法文件改写（含 happiness.ts 新建） + 现有 123 个测试用例大量调整 + 新增 17 场景集成测试的成本，换"未来 v1.7-v2.0 都不再被这类问题反复折磨"的长期收益。

### 2.2 为什么选"价值-成本"架构

**论点 1：性价比天然是"价值 vs 成本"的关系，不是线性加权能表达的**

这个产品叫"这房值不值"——核心问题不是"打多少分"，而是"你得到的（居住质量 + 生活便利 + 幸福源）配得上你付出的（房租 + 通勤 + 压力）吗？"。

旧算法用 `房租×0.30 + 通勤×0.25 + 居住×0.25 + 生活×0.20 - 压力×0.10` 把所有维度拉到一条线上加权，本质上是在算"综合体感分"，不是"性价比"。这导致两类用户在数学上被混在一起：
- A 用户：50% 房租 + 顶级居住（贵但好）
- B 用户：10% 房租 + 破旧居住（便宜但烂）

线性加权下他们的总分接近，但他们的**租房决策逻辑完全不同**——A 是"我愿意为体验付溢价"，B 是"我能省一分是一分"。算法没把这种本质差异表达出来，用户体感就是"分数不合理"。

把"得到"和"付出"先各自聚合、再交叉比较，才能把这两类用户拉开。这是 D10 选 `价值 × 0.65 + (100 - 成本) × 0.35` 而非纯线性加权的根本原因。

**论点 2：维度内不丢信息 + 维度间用价值/成本交叉 = 两层解耦**

D9 / D11 / D10 不是三个独立决策，而是**一组联动的架构升级**，各自负责一层：

| 层 | 决策 | 解决的问题 |
|---|---|---|
| 维度内 | D11 特征向量（mainScore + weakest + strongest） | "信息丢失" + "诊断不可解释" |
| 维度间 | D10 价值/成本公式 | "维度不交叉" + "贵 vs 便宜分差小" |
| 调节项 | D1（city 拆好处/坏处） + D7/D8 把"零散加成"归入幸福/压力指数 | "三重计入"（D1） + "加成不结构化"（D7/D8） |

**这三层缺一不可**：如果只升级维度内（保留 weakest）但维度间还是线性加权，A/B 两类用户的差距问题解决不了；如果只升级维度间但维度内还是单分数，诊断 Modal 就讲不出"居住短板：楼层"这种话——只会说"居住 60 分"，用户问"60 分到底哪 60 哪 40"还是没答案。

**论点 3：为什么不是别的交叉公式（候选 X/Y/Z 被放弃的逻辑）**

D10 的取舍段已经讲过具体候选的得分对比，本节只补"哲学层面"的解释——为什么 W'（0.65/0.35）是这组方案里唯一既"数学可控"又"语义可读"的：

- **候选 X（价值 - 成本 / 2）** 是"对称减法"，听起来合理，但价值和成本不在同一尺度上：你付 30% 房租是"中等成本"，但住到顶级好房是"巨大价值"，它们不该简单相减。D10 测试发现"贵的好房子"与"便宜的破房子"在 X 下分差被严重压缩，正是这种尺度不匹配的表现。
- **候选 Y（价值 / 成本 ROI）** 是金融视角，但需要处理除零、超出 [0,100] 难映射、且非线性太强（成本 = 5 vs 10 差 2 倍，但用户体感是"都很便宜"）。算法的"用户体感对齐"被牺牲。
- **候选 Z（维度乘法）** 强调"短板效应"——任一维度低就全盘压低。但这与产品定位冲突：算法要做"诚实评分"，不是"找茬"。一线高房租配顶级好房（17 场景表中"贵的好房子" 70 分）在乘法公式下会被房租维度的低分严重拖垮，与体感不符。
- **候选 W'（0.65/0.35 加权）** 是"加权减成本"的变种，保留线性的可读性，又通过"价值主导"的权重不对称表达产品哲学（详见 2.3）。

### 2.3 为什么近似对称、价值主导

> D10 的权重设计有 3 个看似随意的数字：`基础分 = 价值×0.65 + (100-成本)×0.35`、`价值内部 0.45/0.35/0.20`、`成本内部 0.40/0.30/0.30`。本节解释为什么是这些数字而不是别的。

**论点 1：近似对称（压力 -10.5 / 幸福 +13.0）比严格对称更符合用户体感**

很多人第一反应是"压力和幸福应该完全对称"（比如都最大传导 ±10 分）。但严格对称在心理学上反而违反用户体感——**损失厌恶**（Kahneman & Tversky 1979/1992 提出）规律指出：人对"损失"的痛感显著大于同等"收益"的快感（经典实验估算约 2 倍）。

所以如果让压力和幸福严格对称（比如都 ±10），用户的实际感受会是"扣得太狠、加得没存在感"。新算法刻意让幸福略大于压力（+13 vs -10.5，比值 1.24），就是为了在心理学层面达到"看起来不对称、但体感对称"的效果。

这种"看似不对称、体感对称"的设计，是对纯数学直觉的一种修正——压力指数走成本侧 0.30 × 0.35、幸福指数走价值侧 0.20 × 0.65，两条传导路径外层权重就不一样，强行追求数字对称反而要把幸福或压力的内权重压成"丑陋的小数"。承认这点不对称、用心理学规律解释它，比硬凑数字更诚实。

**论点 2：价值主导 0.65/0.35 而非 0.5/0.5 或 0.7/0.3**

W' 公式 `价值×k + (100-成本)×(1-k)` 中的 k 取值决定"产品立场"：

| k 值 | 立场 | 测试结果 |
|---|---|---|
| 0.5 / 0.5 | 中立（价值和成本等重） | 与"线性加权"几乎等价，回到旧算法的问题——贵 vs 便宜分差被压缩 |
| 0.7 / 0.3 | 强价值导向 | 17 场景中 80+ 档明显偏少（详见 D10 取舍段），刻度可感知性差 |
| **0.65 / 0.35** | **价值导向 + 成本仍可见** | 80+ 档约 29%，及格、良好、优秀三档都有用户分布 |

选 0.65/0.35 不是因为它"数学最优"，而是因为它在"刻度分布"和"产品哲学"上同时达标。**产品哲学**部分：算法叫"这房值不值"——比起"你付得起吗"，我们更关心"你住得值不值"，所以价值侧权重更大。

**论点 3：价值内部 0.45/0.35/0.20 而非 D10 初稿的 0.40/0.30/0.30**

价值内部 3 子项（居住/生活/幸福）权重调整是"近似对称"约束的直接产物：

```
初稿（价值内 0.40/0.30/0.30）：幸福最大传导 = 100 × 幸福内权重 0.30 × 价值主导系数 0.65 = 19.5 分
                              压力最大传导 = 100 × 压力外权重 0.30 × 成本影响系数 0.35 = -10.5 分
                              比值 19.5/10.5 = 1.86 倍 → 严重不对称，幸福被过度放大

修订（价值内 0.45/0.35/0.20）：幸福最大传导 = 100 × 幸福内权重 0.20 × 价值主导系数 0.65 = 13.0 分
                              压力最大传导 = 100 × 压力外权重 0.30 × 成本影响系数 0.35 = -10.5 分
                              比值 13.0/10.5 = 1.24 倍 → 近似对称，刚好被损失厌恶弥补
```

把 0.10 从幸福转给居住和生活，反而更符合产品定位——"居住 + 生活"是用户**真正每天感受的价值**（采光、噪音、商超），而"幸福指数"（生活小细节、合同期、城市好处）是**长期满足感**，权重应略低。

这个调整不是算法层面的"调参玄学"，而是从"压力/幸福近似对称"这个高层约束反推出来的——一旦把约束写清楚，权重就自然出来了。

### 2.4 边界 & 不做的事

> 算法设计中，"不做什么"和"做什么"同样重要。本节记录在讨论过程中**被认真考虑过、最终放弃**的想法，避免未来重读文档时被诱惑回头。

**不做 1：不引入"性价比"作为独立维度**

讨论早期曾有想法："要不要在 4 客观维度之外，加一个'性价比'维度作为第 5 维？"——被否决。

理由：**性价比是整个算法的输出，不是输入。** 把它当维度会陷入循环定义——性价比维度本身又怎么算？要么用其他 4 维加权（那就还是线性加权，不解决问题），要么单独打分（那就是用户主观估计，算法的"客观"基础瓦解）。

D9 架构升级正是把"性价比"从"某个维度"提升到"总分公式的整体语义"——价值/成本两侧的交叉就是性价比的天然数学表达。

**不做 2：不实现 dispersion / completeness 特征字段**

D11 候选 B 曾建议特征向量包含 `dispersion`（子项分数标准差）和 `completeness`（数据填写率）。被改为候选 C（仅 mainScore + weakest + strongest）。

理由：
- D10 总分公式不依赖这两个字段——加进来也不会改变任何用户能看到的分数
- 诊断 Modal 不需要"你的居住分数离散度 0.18"这种工程化指标，用户只想知道"短板是什么"
- 渐进式原则：未来 v1.7+ 若发现真需要再加（如"标签强项判定"），不会有破坏性升级——`DimensionFeature` 是开放结构

这是典型的**克制过度设计**：能用最小集解决的问题，就不要为"未来可能用到"提前实现。

**不做 3：不用 sigmoid 等"全程敏感"的房租曲线**

D12c 候选中有 sigmoid（S 型曲线全程敏感）和 I+（双侧高斯衰减，低占比也扣分），都被放弃。

理由：算法的产品哲学是**中立、不评价用户选择**：
- sigmoid 在基准点（30%）附近骤降，给用户的体感是"我刚跨基准 1%，算法就突然惩罚我"——这是算法在替用户判断"该不该住这么贵"，越界了
- I+ 让低占比（远低于基准 30%）也扣分，潜台词是"你这么便宜肯定有问题"——但算法没法分辨"远郊 / 朋友的房 / 公司补贴 / 老破小"，强行扣分就是在凭主观推测下结论

候选 K（低占比饱和 100 + 高占比 exp 衰减）保留了"低占比死区"，正是为了让算法"只评价客观财务压力，不评价用户的生活方式"。死区代价是月薪在低占比段微调时房租维度不动，但月薪变化会通过压力指数的 `incomeBurden` 间接传导（月薪 → incomeBurden → 压力 → 总分），整体可接受。

**不做 4：不在 v1.6.3 接入真实房价 / 通勤 API**

v2.0 路线图里有"接入贝壳/链家房价数据"和"高德通勤 API"，但 v1.6.3 范围内不做。

理由：v1.6.3 的目标是**修好算法心智模型**——把"加权求和"换成"特征推理"。这个目标的边界是"只动算法层 + 配套数据结构"，**不碰外部数据源**。

如果在同一个版本既改算法又接 API，会引入两类无关复杂度：
- 网络层：API 限流、缓存、降级策略
- 隐私层：用户位置/小区信息脱敏
- 测试层：mock 外部数据让单元测试可重复

把这些与算法重构混在一起，调试会变成"是算法 bug 还是 API bug"的猜谜——违背 AGENTS.md 里"渐进式优化"的协作约定。

```typescript
// 新逻辑伪代码
export function calculateScore(rawInput) {
  const input = normalizeInput(rawInput)

  const rentFeature = calcRentFeature(input)
  const commuteFeature = calcCommuteFeature(input)
  const liveFeature = calcLiveFeature(input)
  const lifeFeature = calcLifeFeature(input)
  const stressFeature = calcStressFeature(input)
  const happinessFeature = calcHappinessFeature(input)

  // 价值侧
  const value =
    liveFeature.mainScore * VALUE_WEIGHTS.live +
    lifeFeature.mainScore * VALUE_WEIGHTS.life +
    happinessFeature.mainScore * VALUE_WEIGHTS.happiness

  // 成本侧（房租/通勤反转，压力不反转）
  const cost =
    (100 - rentFeature.mainScore) * COST_WEIGHTS.rent +
    (100 - commuteFeature.mainScore) * COST_WEIGHTS.commute +
    stressFeature.mainScore * COST_WEIGHTS.stress

  // 基础分（价值主导）
  const baseScore = value * VALUE_DOMINANCE + (100 - cost) * COST_INFLUENCE

  // 短板惩罚
  let shortfallPenalty = 0
  for (const dim of [rentFeature, commuteFeature, liveFeature, lifeFeature]) {
    if (dim.mainScore < SHORTFALL_THRESHOLD) {
      shortfallPenalty -= (SHORTFALL_THRESHOLD - dim.mainScore) * SHORTFALL_PENALTY_FACTOR
    }
  }

  const totalScore = clamp(baseScore + shortfallPenalty, 0, 100)

  return {
    totalScore: Math.round(totalScore),
    rentRatio: input.rent / Math.max(input.income, 1) * 100,
    rentFeature, commuteFeature, liveFeature, lifeFeature, stressFeature, happinessFeature,
    persona: pickPersona(totalScore).label,
    housingType: input.housingType,
    // 兼容字段（P5 清理时统一删除）
    commuteScore: commuteFeature.mainScore,
    liveScore: liveFeature.mainScore,
    lifeScore: lifeFeature.mainScore,
    stress: stressFeature.mainScore,
  }
}
```

### 3.3 测试策略

#### 3.3.1 单元测试（每个维度独立验证）

每个 `*.test.ts` 至少覆盖：
- **核心场景**：典型用户输入 → 预期 mainScore
- **边界场景**：所有子分 0 / 所有子分 100 / 单项极端
- **weakest/strongest 选取**：贡献值最低/最高的子项被正确识别
- **特征向量结构**：返回类型符合 `DimensionFeature`

示例 `housing.test.ts`：

```typescript
describe('calcLiveFeature', () => {
  it('完美居住 → mainScore 100', () => {
    const result = calcLiveFeature({ sunlight: 5, noise: 1, ... })
    expect(result.mainScore).toBe(100)
    expect(result.weakest).toBeNull() // 所有子项满分时无短板
  })

  it('采光最差 → weakest = sunlight', () => {
    const result = calcLiveFeature({ sunlight: 1, noise: 3, ... })
    expect(result.weakest?.key).toBe('sunlight')
  })

  it('权重正确：sunlight 0.20 → 占主导', () => {
    // 输入：sunlight=1（scaleFromFive→0分）；noise=1（反向，noise=1→100分）；其他 5 项均=5（→100分）
    // 计算：0×0.20 + 100×(0.18+0.16+0.15+0.13+0.10+0.08) = 0 + 100×0.80 = 80
    const result = calcLiveFeature({ sunlight: 1, noise: 1, bathroom: 5, condition: 5, kitchen: 5, floor: 5, utility: 5 })
    expect(result.mainScore).toBeCloseTo(80, 0)
  })
})
```

#### 3.3.2 集成测试（17 场景验证）

新建 `app/lib/score/integration.test.ts`：

```typescript
const SCENARIOS = [
  { name: '真·完美', rent: 0, income: 50000, /* 子分都 100 */, expected: 100, tolerance: 3 },
  { name: '一线 4w 精致小户', /*...*/, expected: 92, tolerance: 3 },
  // ... 17 个场景
]

describe('17 场景集成测试', () => {
  SCENARIOS.forEach(scenario => {
    it(scenario.name, () => {
      const result = calculateScore(buildInput(scenario))
      // 显式区间断言，避免 toBeCloseTo 的 precision 语义混淆
      expect(result.totalScore).toBeGreaterThanOrEqual(scenario.expected - scenario.tolerance)
      expect(result.totalScore).toBeLessThanOrEqual(scenario.expected + scenario.tolerance)
    })
  })
})
```

> ⚠️ **断言写法说明**：避免使用 `toBeCloseTo(expected, -1)`——它的 precision 参数是"小数位数"，-1 对应容差 5、0 对应容差 0.5，与"±3 分"语义不直接对应。用显式 `toBeGreaterThanOrEqual` / `toBeLessThanOrEqual` 更清晰。

> 📌 **expected 回填策略**：ADR-D10 的 17 场景 `expected` 是 D7 修订前的估算值（约 ±2 分浮动）。**实施步骤**：
> 1. P1 阶段写完算法后，先跑一遍打印各场景实际 totalScore
> 2. 若与表中 expected 偏差 ≤3 分 → 视为"正常浮动"，把实际值回填到测试 expected
> 3. 若偏差 >3 分 → 暂停实施，检查是否算法实现 bug 或 ADR 设计本身需要调整（回到 D10 重新讨论）
> 4. 回填完成后保留 `tolerance` 容忍后续小调整，但所有断言基于"真实算法输出"而非"估算值"
